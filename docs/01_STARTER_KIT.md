# Стартер-кіт: паралельна AI-розробка з зовнішньою пам'яттю

> **Що це:** готовий набір файлів і промптів, який студент кладе у свій
> проект і отримує ту саму систему «оркестратор + робочі чати + пам'ять»,
> що описана в `00_JOB_DESCRIPTION.md`. Розрахований на Claude Code
> (CLI або десктоп) і git-репозиторій. Нічого платного, крім самого Claude,
> не потрібно.

---

## Крок 0. Передумови

- Проект — git-репозиторій (якщо ні: `git init` + перший коміт).
- Встановлений Claude Code; чати запускаються З ТЕКИ репозиторію
  (інакше вони не бачать конституцію).
- GitHub (або будь-який remote) — щоб push був страховкою.

## Крок 1. Створи структуру пам'яті (один раз)

```
<репо>/
  CLAUDE.md                  ← конституція (шаблон нижче) — читається КОЖНИМ чатом автоматично
  coordination/
    WORKSTREAMS.md           ← хто над чим працює зараз (рядок на чат)
    DECISIONS.md             ← прийняті рішення З ПОЯСНЕННЯМ ЧОМУ (анти-кола!)
    BACKLOG.md               ← свідомо відкладене, з причиною
    MISTAKES.md              ← граблі: помилка → корінь → правило
    PROJECT_MAP.md           ← що вже збудовано, що канон, що дубль/мертве
    inbox/                   ← листування чатів: from-<хто>-to-<кому>-<тема>.md
    log/                     ← журнал: YYYY-MM-DD.md, 3-7 рядків від кожного чату
```

Усі файли — у git. Це принципово: **пам'ять, якої нема в git, не існує.**

## Крок 2. Поклади в корінь репо `CLAUDE.md` (шаблон)

Скопіюй блок нижче у файл `CLAUDE.md` в корені свого репозиторію і заповни
`<...>`-місця. Claude Code автоматично підвантажує цей файл у кожен чат,
відкритий у цій теці, — тому правила діють на всі чати без нагадувань.

```markdown
# Конституція проекту <НАЗВА>

## Ролі (жорстко)

- **КООРДИНАТОР** — рівно ОДНА сесія. Ознака: її рядок у
  coordination/WORKSTREAMS.md позначений `[COORD]` і має СЬОГОДНІШНЮ дату.
  Тільки координатор: мерджить ризикові PR, деплоїть, чіпає спільні ресурси
  (встановлення залежностей, конфіги, CI). Якщо рядок протух (дата не
  сьогодні) — роль вільна: перший чат, якому вона потрібна, бере її і
  оновлює рядок.
- **РОБОЧИЙ ЧАТ** — усі інші. Не впевнений, що ти координатор → ти робочий чат.

## Правила робочого чату

1. ПЕРЕД першим редагуванням — створи власний git worktree (інструмент
   EnterWorktree). Ніколи не редагуй файли поза своїм деревом.
2. `git status` на старті: бачиш чужі незакомічені зміни — НЕ чіпай,
   не роби reset/checkout/stash/clean — це робота іншого чату.
3. НЕ запускай встановлення залежностей (npm/pnpm/pip install) — це спільний
   ресурс, тільки координатор. Потрібен пакет → інбокс-файл координатору.
4. Здача: commit → push своєї гілки → PR. Ризикова зона (auth, платежі,
   схема БД, доступи, розсилки) → НЕ мерджити самому, віддай координатору
   через inbox/. Решта — мерджити можна після зеленого CI.
5. НІКОЛИ не ковтай код виходу перевірок (`| tail`, `|| true` навколо
   тестів/лінтера/білда заборонені). Червоне не мерджиться. Крапка.
6. Нічого не видаляй з дисків власника. Ніколи.

## Пам'ять: обов'язкові ритуали

### На старті КОЖНОЇ сесії (по порядку)

1. `git status` (чуже брудне дерево? → worktree).
2. Прочитай coordination/WORKSTREAMS.md → додай/онови свій рядок
   (хто ти, над чим, у якому worktree, дата).
3. Прочитай свій інбокс: усі файли `coordination/inbox/`, адресовані тобі
   (`from-…-to-<я>-….md`).

### 🔒 Перед НЕТРИВІАЛЬНОЮ задачею (анти-кола — найважливіше правило)

Ми вже будували ті самі речі по 2-3 рази, бо нові чати не звірялися.
Тому перед «збудуй/спроектуй X» ти ЗОБОВ'ЯЗАНИЙ:

1. Прочитати coordination/DECISIONS.md — чи X уже вирішено робити інакше /
   не робити взагалі (і чи причина ще актуальна).
2. Прочитати coordination/PROJECT_MAP.md + грепнути кодову базу — чи X
   уже не існує (повністю або частково). «Грепни, перш ніж специфікувати».
3. Глянути coordination/BACKLOG.md — чи X не відкладено свідомо.

Перший рядок твоєї відповіді на таку задачу — вердикт звірки: «вже є отут…» /
«відхилено тоді-то, бо…» / «у беклозі, бо…» / «в пам'яті чисто, роблю».

### Під час роботи

- Прийняв рішення (архітектура, бібліотека, «робимо/не робимо») → одразу
  рядок у DECISIONS.md: дата, рішення, ЧОМУ, альтернативи що відкинули.
- Відклав щось свідомо → рядок у BACKLOG.md у ТОМУ Ж коміті.
- Наступив на граблі → рядок у MISTAKES.md: симптом → корінь → правило.
- Комітити: текст — після кожного файлу; код — кожні ≤30 хв. Push одразу.
  Untracked-файл старший за 10 хвилин — порушення.

### Наприкінці сесії

- 3-7 рядків у coordination/log/YYYY-MM-DD.md: що здано (PR-лінк),
  що не закінчено, що передано далі.
- Онови свій рядок у WORKSTREAMS.md (або познач завершеним).

## Комунікація між чатами

- Канал — ФАЙЛИ в git: coordination/inbox/from-<я>-to-<кому>-<тема>.md
  (закомічено і запушено). Повідомлення в UI — лише «нудж», не канал.
- Прокинувся з будь-якої причини → git fetch + перечитай свій інбокс.
- Жодних таймер-петель «перевіряй щоN хвилин» — тільки подієва модель.

## Звітність власнику

- Власник НЕ читає код. Йому — тільки: що готово (лінком), що зламалось
  (простою мовою), і рідкі бізнес-питання «так/ні» (гроші, зовнішні
  повідомлення, доступи). Технічні питання вирішуй сам і документуй
  у DECISIONS.md.
- «Зробив 4/6 і питання» власник читає як «готово» — тому або доводь до
  кінця, або яви це рядком у BACKLOG з причиною.
- Тихий успіх заборонено: операція, що нічого не зробила, мусить впасти
  гучно. Після деплою — жива перевірка незалежним запитом, не «звіт агента».
```

## Крок 3. Заповни стартовий стан пам'яті (15 хвилин, один раз)

- **PROJECT_MAP.md** — перелічи, що ВЖЕ існує в проекті (модулі, сторінки,
  скрипти), і познач дублікати/мертве. Це насіння анти-кіл.
- **DECISIONS.md** — 3-5 найважливіших уже прийнятих рішень з «чому»
  (стек, структура, що вирішили не робити).
- **WORKSTREAMS.md** — порожня таблиця: `| чат | зона | worktree | дата |`.
- Решта файлів — порожні з заголовком. Закоміть і запуш усе.

## Крок 4. Промпт координатора (перший чат дня)

```
Ти — КООРДИНАТОР цього репозиторію (єдина сесія з такою роллю).
1) git status; прочитай CLAUDE.md, coordination/WORKSTREAMS.md і весь
   coordination/inbox/ — розгреби, що назбиралося.
2) Запиши себе в WORKSTREAMS.md рядком [COORD] з сьогоднішньою датою.
3) Дай мені зведення: що змерджено/зламано/чекає рішення (тільки
   бізнес-рівень, без коду).
Далі чекай задач. Ризикові PR інших чатів гейтиш і мерджиш ти.
```

## Крок 5. Промпт робочого чату (кожен новий чат)

```
Ти — РОБОЧИЙ чат у цьому репозиторії. Ти НЕ координатор.
1) Прочитай CLAUDE.md повністю і підтверди одним рядком, що приймаєш
   правила: власний worktree, ніяких install, здача через PR, ризикове —
   координатору, анти-кола перед нетривіальним.
2) Виконай стартовий ритуал з CLAUDE.md (git status → worktree →
   WORKSTREAMS → інбокс).
3) Перед задачею — обов'язкова звірка анти-кіл (DECISIONS + PROJECT_MAP +
   BACKLOG + греп). Перший рядок відповіді — вердикт звірки.

Задача: <ОПИС ЗАДАЧІ>
```

## Крок 6 (опційно, коли доросли). Автоматизація шарів L1-L2

Мінімальна система вище — це шар L3 (правила + рішення), і його вистачає
на 80% користі. Коли сесій стане багато:

1. **L1:** SessionEnd-хук Claude Code, що експортує транскрипт кожної сесії
   в markdown-архів (окремий приватний репо; НЕ пушити публічно — там PII).
2. **L2:** нічний скрипт, що робить вижимку кожної нової сесії («зробили /
   рішення / незакінчене / граблі») через безкоштовну LLM і складає у
   digests/. Агрегат WIP.md — «усе незакінчене» одним файлом.
3. **Пошук:** локальний семантичний індекс (наприклад Chroma) по вижимках і
   транскриптах, підключений до Claude як MCP — тоді «що ми вирішили по X»
   стає одним викликом навіть при тисячах сесій.

## Як оновлюватись (раз на місяць достатньо)

```bash
bash /шлях/до/parallel-ai-dev/scripts/update-kit.sh --check   # лише перевірити
bash /шлях/до/parallel-ai-dev/scripts/update-kit.sh           # оновити клон і звірити
```

Запускати з кореня СВОГО проєкту.

**Чому перевірка з двох пунктів.** Комплект ставиться копіюванням шаблонів до
тебе, тому «чи в мене свіжа версія» — це два різні питання: чи свіжий сам клон
комплекту і чи бачив ти зміни шаблонів, що прийшли в клон після встановлення.
Перевірка, яка дивиться лише на друге, зелена **назавжди**: старий клон вічно
«відповідає» старій інсталяції, і людина роками сидить на торішній версії,
впевнена, що все гаразд. Тому перша ланка завжди ходить на GitHub, а якщо не
достукалась — каже про це прямо і виходить помилкою, а не «все свіже».

| Що показує                        | Що означає                                                  |
| --------------------------------- | ----------------------------------------------------------- |
| `1/2 ✅` і `2/2 ✅`                | усе свіже                                                   |
| `1/2 ⚠️ Клон ВІДСТАВ`             | на GitHub новіша версія — запусти без `--check`             |
| `1/2 ✅ … + твої коміти`          | ти правив сам комплект; з GitHub тобі нічого не бракує      |
| `1/2 ⚠️ Клон РОЗІЙШОВСЯ`          | і своє є, і чужого бракує — автооновлення не пройде         |
| `2/2 ⚠️ Інсталяція ВІДСТАЛА`      | шаблони змінились після встановлення; скрипт назве які саме |
| `2/2 ⚠️ Не знаю, з якої версії`   | немає мітки `coordination/.kit-version` — звірся раз вручну  |
| `❌ Не можу перевірити`           | не достукався до GitHub. Це **не** «все свіже»              |

Власний коміт у самому комплекті — не привід червоніти: з GitHub тобі при цьому
нічого не бракує. Перевірка, яка кричить на справному стані, вчить людину
ігнорувати червоне, і тоді справжня проблема теж пройде повз.

**Твої файли скрипт не перезаписує ніколи.** Ти заповнив шаблони своїм змістом —
машина не знає, де твоє, а де наше. Друга ланка не «оновлює», а називає файли,
які змінились у комплекті, щоб ти переніс зміни свідомо.

## Найчастіші способи все зламати (чек самоперевірки)

| Симптом                                     | Порушене правило                                  |
| ------------------------------------------- | ------------------------------------------------- |
| Чат «загубив» роботу іншого чату            | не було worktree / чіпав чуже дерево              |
| Той самий модуль збудовано вдруге           | пропущена звірка анти-кіл перед стартом           |
| «Ми ж це вирішували!» — а ніхто не пам'ятає | рішення не записано в DECISIONS.md з «чому»       |
| Зламалась збірка у ВСІХ чатах одразу        | робочий чат запустив install у спільні залежності |
| Червоний CI опинився в main                 | обхід safe-merge / зʼїдений код виходу            |
| «Задеплоєно», а на проді старе              | тихий успіх: ніхто не перевірив живим запитом     |
| Задача тижнями «висить» ні там ні там       | «зробив 4/6» без рядка в BACKLOG                  |
| Прибрали покинуте дерево — і зник код у головній теці | дерево видалили рекурсивно замість `git worktree remove` |
| Файли пам'яті є, але всі порожні або торішні | завели файл і жодного разу не перевірили, чи він живий |

### Прибирання робочих дерев — окремо, бо це найдорожча помилка з усіх

Дерева накопичуються швидше, ніж здається: у нас їх набралось 130 при десятку
активних чатів. Прибирати їх треба — але рівно одним способом:

```bash
git worktree list                 # подивитись, що взагалі є
git worktree remove <шлях>        # ЄДИНИЙ правильний спосіб
git worktree prune                # почистити записи про вручну знесені дерева
```

**Чому не можна просто видалити теку.** Усередині дерева лежать службові посилання
(symlink/junction) на спільні залежності головної теки — так менеджери пакетів
економлять місце. Рекурсивне видалення проходить крізь такі посилання і вигрібає
те, на що вони вказують, тобто живий код головного проєкту. `git worktree remove`
і `rmdir` крізь посилання не ходять; `rm -rf`, `Remove-Item -Recurse` і видалення
теки мишкою — ходять.

**Перевірка, чи є у твоїх деревах така міна** (запусти з кореня проєкту):

```bash
# Linux/macOS
find .git/worktrees -maxdepth 0 >/dev/null 2>&1 && \
  git worktree list | awk '{print $1}' | while read d; do
    [ -L "$d/node_modules" ] && echo "МІНА: $d/node_modules -> $(readlink "$d/node_modules")"
  done
```

```powershell
# Windows
git worktree list | ForEach-Object { ($_ -split '\s+')[0] } | ForEach-Object {
  $n = Join-Path $_ 'node_modules'
  if (Test-Path $n) { $i = Get-Item $n -Force
    if ($i.LinkType) { "МІНА: $n -> $($i.Target)" } }
}
```

Кожен виведений рядок — дерево, яке не можна видаляти як звичайну папку.
