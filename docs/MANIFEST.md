# MANIFEST — з чого складається кіт і кому належить кожен файл

> Це технічний довідник комплекту. Головне питання, на яке він відповідає:
> «якщо кіт оновиться — які МОЇ файли він ніколи не зачепить?»

## Три класи файлів

| Клас             | Хто пише                    | Що з ним робить оновлення кіту                        |
| ---------------- | --------------------------- | ------------------------------------------------------ |
| **kit-owned**    | комплект                    | замінюється новою версією; твої правки в ньому втрачаються — тому не редагуй |
| **user-owned**   | ти                          | НІКОЛИ не перезаписується; інсталятор створює його лише якщо файла немає |
| **append-only**  | обидва                      | кіт може ДОПИСАТИ рядок, але не переписує наявний вміст |

## Файли у ТВОЄМУ проєкті після встановлення

| Файл | Клас | Призначення |
| --- | --- | --- |
| `CLAUDE.parallel-ai-dev.md` | kit-owned | правила кіту (ролі, worktree, пам'ять, анти-кола, протокол спільної пам'яті) |
| `CLAUDE.md` | user-owned | ТВОЯ конституція: рядок імпорту `@CLAUDE.parallel-ai-dev.md` + зони твого проєкту |
| `coordination/SETUP.md` | user-owned | три декларації: visibility / mode / constitution |
| `coordination/DECISIONS.md` | user-owned | що вирішено і ЧОМУ (включно з «свідомо НЕ робимо») |
| `coordination/MISTAKES.md` | user-owned | симптом → корінь → правило |
| `coordination/PROJECT_MAP.md` | user-owned | що в проєкті ВЖЕ існує (насіння анти-кіл) |
| `coordination/BACKLOG.md` | user-owned | свідомо відкладене |
| `coordination/WORKSTREAMS.md` | user-owned | хто з чатів над чим працює; рядок `[COORD]` |
| `coordination/inbox/README.md` | kit-owned | правила листування між чатами |
| `coordination/inbox/*.md` (листи) | user-owned | самі листи; не видаляються |
| `coordination/log/README.md` | kit-owned | правила журналу сесій |
| `coordination/log/*.md` (записи) | user-owned | журнал; append-only за змістом |
| `coordination/.kit-version` | kit-owned | мітка встановленої версії (номер, напр. `2.0.0`) |
| `coordination/.selfcheck.conf` | user-owned | перевизначення шляхів + прапорці (див. нижче); опційний |
| `.gitattributes` | append-only | кіт дописує `*.sh text eol=lf`, більше нічого не чіпає |

Файли, які кіт НЕ створює і НЕ читає: будь-яка персональна пам'ять поза репо
проєкту. Кіт — це пам'ять КОМАНДИ ПРОЄКТУ в git, і тільки вона.

## Нормативні перевірки R1–R9 (довідкова копія; поведінку визначає self-check.sh)

| # | Перевірка | Червоне означає |
| --- | --- | --- |
| R1 | обов'язкові файли існують | щось не розгорнуто — запусти інсталятор |
| R2 | файли пам'яті відстежуються git-ом | untracked = незастрахований (перший коміт ще не зроблено — теж сюди) |
| R3 | у відстежуваних файлах пам'яті нема незакомічених правок | «поправив і забув закомітити» |
| R4 | файли пам'яті не задавлені `.gitignore` | пам'ять мовчки не потрапляє в репо |
| R5 | конституція під'єднана | `CLAUDE.md` без рядка `@CLAUDE.parallel-ai-dev.md` (або, при `constitution: self-managed`, власна конституція не згадує файли звірки) |
| R6 | карта проєкту заповнена | порожній шаблон — анти-кола нема з чого працювати |
| R7 | у DECISIONS є хоч один запис | рішення ніде не фіксуються |
| R8 | SETUP.md заповнений допустимими значеннями | декларацій visibility/mode/constitution немає або з помилкою |
| R9 | `mode: team` → ≥2 робочих дерева | паралельні чати без ізоляції затирають одне одного |

Принципи: **зелене мовчить** (друкуються тільки порушення — список на екрані і є
чек-лист); шляхи беруться з `.selfcheck.conf`, якщо він є (перевірка, що кричить
на справному стані, вчить ігнорувати червоне); повідомлення називають ДОЗВОЛЕНІ
значення, а не цитують твій вміст.

## `.selfcheck.conf` — підлаштування під свою розкладку

Файл `coordination/.selfcheck.conf`, формат «КЛЮЧ=шлях», по рядку:

```
DECISIONS=docs/DECISIONS.md
PROJECT_MAP=coordination/PRODUCT_MAP.md
BACKLOG=.ai-context/BACKLOG.md
WORKSTREAMS=../_HQ/WORKSTREAMS.md    # можна й поза репо — тоді git-перевірки його пропускають
STRICT_ADVISORY=1                    # червоне з розширеної діагностики теж валить перевірку
```

Наявність конфіга також вмикає розширену діагностику в кожному прогоні
`self-check.sh` (без конфіга — тільки за прапорцем `--full`).

Відомий конфлікт, вирішення якого відкладено у 2.1: якщо ти свідомо
адаптував kit-owned файл (наприклад, `coordination/log/README.md`) під свій
процес, оновлення кіту захоче його замінити. У 2.1 з'явиться `--upgrade` з
рядком `KIT_KEEP=<шлях>` у конфі — декларований спосіб сказати «цей файл мій,
не онови». До того часу `update-kit.sh` і так нічого не перезаписує — він лише
називає файли, що змінилися.

## Версіювання

Одна цифра в трьох місцях, завжди однакова: git-тег `vX.Y.Z` ↔ файл `VERSION`
↔ шапка README. Інсталятор ставить цю цифру в `coordination/.kit-version`
твого проєкту; `update-kit.sh` розуміє і цифру (з 2.0.0), і старий хеш коміту.
