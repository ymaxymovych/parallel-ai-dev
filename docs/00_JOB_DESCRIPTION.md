# Job Description: Оркестратор паралельної AI-розробки з зовнішньою пам'яттю

> **Для кого:** студенти курсів, що доросли до управління кількома Claude-чатами
> одночасно. **Звідки взято:** це не теорія — це дзеркало робочої системи
> AIAdvisoryBoard станом на 09.08.2026 (7+ паралельних чатів щодня, сотні
> змерджених PR, реальні інциденти та правила, що з них виросли).
> **Що це за документ:** опис РОБОТИ, яку виконує зв'язка «людина, чат-оркестратор,
> N робочих чатів і зовнішня пам'ять». Сетап-інструкція — у `01_STARTER_KIT.md`.

---

## 1. Навіщо ця роль існує

Один чат Claude — це один розробник із амнезією: він геніальний усередині сесії
і забуває все між сесіями. Коли задач стає більше, ніж влазить в один чат,
з'являються дві проблеми, які НЕ розв'язуються «просто відкрию ще один чат»:

1. **Паралельні чати затирають роботу одне одного.** Два чати в одній теці —
   це два розробники за однією клавіатурою. Один робить `git checkout`, поки
   інший має незбережені зміни → робота зникає без сліду.
2. **Ніхто нічого не пам'ятає.** Рішення, прийняте у вівторок у чаті №3,
   в середу в чаті №5 приймається заново — інакше. Помилка, виправлена місяць
   тому, повторюється, бо «граблі» ніде не записані.

Відповідь — **розподіл ролей** (хто що має право робити) + **зовнішня пам'ять**
(усе важливе живе у файлах у git, а не в голові чату).

---

## 2. Ролі

### 2.1. Власник (людина)

Єдина людина в системі. НЕ читає код і НЕ мусить. Що робить:

- Ставить задачі (у будь-який чат, простою мовою).
- Приймає **тільки бізнес-рішення**: витратити гроші, написати реальній людині,
  масова розсилка, зміна доступів. Усе технічне вирішують чати самі.
- Читає звіти по факту виконання, а не «питання в процесі».

Головний принцип: кожне зайве питання-підтвердження до власника множиться на
N паралельних чатів і зупиняє всю систему. Тому чати вирішують самі й
аргументують по факту; власник перекриє, якщо не згоден.

### 2.2. Чат-оркестратор (координатор)

**Рівно один.** Працює з головної теки репозиторію (main). Це «тімлід,
DevOps і диспетчер» в одній сесії. Обов'язки:

| Обов'язок           | Що конкретно                                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Реєстр потоків      | Тримає файл WORKSTREAMS.md: хто з чатів над чим працює, щоб зони не перетиналися                                                |
| Гейт ризикових змін | PR, що чіпає auth/платежі/схему БД/доступи/розсилки — мерджить ТІЛЬКИ координатор, після власної технічної+безпекової перевірки |
| Деплой і прод       | Сервер, cron, env, спільні ресурси (залежності, git-хуки) — тільки координатор                                                  |
| Ремонт спільного    | Зламані спільні залежності, конфлікти між чатами, «розрулювання» інцидентів                                                     |
| Розсилка інструкцій | Нові правила → інбокс-файли всім чатам + нудж                                                                                   |
| Звітність           | Лог дня: що змерджено, що задеплоєно, що зламалось і чому                                                                       |

Роль — **самопризначувана і видима**: координатор записує себе рядком у
WORKSTREAMS.md зі свіжою датою. Протух рядок (дата не сьогоднішня) — роль
вільна, її бере інший чат і оновлює рядок. Це захист від «координатор зник,
і ніхто не мерджить».

### 2.3. Робочі чати (виконавці)

Усі інші. Кожен:

- Живе у **власному git worktree** (ізольована копія репо) — створює його ДО
  першого редагування. Ніколи не редагує поза своїм деревом.
- Отримує задачу → робить → комітить часто → пушить свою гілку → відкриває PR.
- **Low-risk** зміни мерджить сам через захищений скрипт (що перевіряє CI).
  **Ризикові** — віддає координатору через інбокс-файл.
- Звітує письмово: інбокс-файл координатору + рядок у лог дня.
- Прокинувся з будь-якої причини → першим кроком читає свій інбокс.

Правило самоідентифікації: **не впевнений, що ти координатор — значить ти
робочий чат.** Стань у worktree.

## 3. Зовнішня пам'ять (метод Карпати)

Ідея Andrej Karpathy: пам'ять агента — це шари дистиляції, як у людини:
сирий досвід → щоденник → зведення → правила життя. У нас чотири шари:

```
L0 сирі джерела ──► L1 повні транскрипти ──► L2 вижимки ──► L3 правила (завжди в контексті)
                            └───────── семантичний пошук по всьому ─────────┘
```

| Шар    | Що це                                                            | Хто пише                        | Приклад у нас                            |
| ------ | ---------------------------------------------------------------- | ------------------------------- | ---------------------------------------- |
| **L0** | Сирі логи сесій, дзвінки, експорти                               | автоматика                      | `.jsonl` усіх Claude-сесій               |
| **L1** | Читабельні повні транскрипти                                     | хук після кожної сесії          | `MyKnowledges/Claude Code History/`      |
| **L2** | Вижимка кожної сесії: «зробили / рішення / незакінчене / граблі» | нічний скрипт (безкоштовна LLM) | `MyKnowledges/digests/`                  |
| **L3** | Правила і констітуція: маленькі, завжди в контексті              | чат наприкінці сесії + людина   | `CLAUDE.md`, `memory/*.md`, `BACKLOG.md` |

**Чому шари, а не один великий файл:** L3 мусить бути МАЛИМ (він у кожному
контексті кожного чату). Усе об'ємне живе нижче і дістається пошуком.

### Що саме зберігається (категорії L3)

- **Конституція** (`CLAUDE.md` в корені репо) — правила, які діють завжди:
  ролі, заборони, конвеєр здачі, git-дисципліна. У git → їх бачить КОЖЕН чат
  автоматично, незалежно від акаунта.
- **Рішення** — що вирішили і ЧОМУ (щоб не передиктовувати). З датою.
- **Граблі** — помилки з поясненням кореня: «мок-тести не ловлять NULL у SQL»,
  «DEPLOY SKIPPED виглядає як успіх». Найцінніший шар: без нього помилки циклічні.
- **Беклог** — свідомо відкладене. Правило: відклав — запиши в тому ж коміті,
  інакше «відкладено» = «забуто».
- **Незакінчене** — щоб наступна сесія продовжила, а не почала заново.

### Правила користування пам'яттю (retrieval)

1. **Перед нетривіальною задачею** — пошук «що ми вже вирішили по X»
   (семантичний пошук або грепи по вижимках). Найдорожча помилка — заново
   пройти вже пройдене коло.
2. **Свіже цієї сесії** — з контексту розмови; **вчорашнє і старше** — з пам'яті.
3. **Наприкінці значущої сесії** — записати 0-3 нові пам'яті (консервативно:
   тільки те, що реально допоможе наступним сесіям).

### 🔒 Запобіжник «анти-кола» (проти проектів, зроблених по 2-3 рази)

Окремий, найважливіший ритуал. У нас він з'явився після того, як ті самі
проекти реально будувалися ДВІЧІ й ТРИЧІ (різними чатами, у різних папках,
трохи інакше) — бо кожен новий чат «не знав», що це вже є.

Механізм із трьох частин, усі три обов'язкові:

1. **Рішення записуються З ПОЯСНЕННЯМ.** Кожне «робимо X» і кожне «НЕ робимо
   X» лягає у файл рішень з датою і рядком «чому саме». Рішення без «чому» —
   напівмертве: наступний чат не зможе оцінити, чи причина ще актуальна,
   і перевирішить заново.
2. **Карта того, що вже існує.** Один файл-реєстр проектів/модулів: назва,
   статус (живий/пауза/покинутий/дубль), що з дублів КАНОН. Правило: не
   «знаходити» здогадкою, де в проекті X — звіритися з картою. У нас
   половина «знайдених» папок виявлялась мертвими дублями.
3. **Кожен новий чат ЗВІРЯЄТЬСЯ перед стартом.** У стартовому чек-листі
   сесії стоїть примусовий крок: перед нетривіальною задачею — прочитати
   файл рішень + грепнути кодову базу «чи X уже не існує» + глянути беклог
   «чи X не відкладено свідомо». Формула: **«грепни, перш ніж
   специфікувати»**. Тільки після цього — писати ТЗ чи код.

Тест, що запобіжник працює: новий чат, отримавши задачу «збудуй X», першою
відповіддю каже або «X вже є отут, ось стан» / «X свідомо відхилено тоді-то,
бо …» / «X у беклозі з причиною …» — або «в пам'яті чисто, будую». Якщо чат
одразу кидається будувати — запобіжник не налаштований.

## 4. Ключові протоколи (вижимка з бойових інцидентів)

Кожне правило тут оплачене реальною втратою:

1. **Untracked = незастрахований.** Файл, що не в git, зникає без сліду
   (у нас: disk-cleanup з'їв ~1500 рядків роботи, відновили 80%).
   → Комітити після кожного файлу тексту, кожні ≤30 хв коду. Push одразу.
2. **Один чат = один worktree.** (У нас: чати в одній теці затирали одне одного.)
3. **Спільні ресурси чіпає тільки координатор.** (У нас: перерваний
   `pnpm install` з робочого чату випотрошив 188 пакетів спільної теки
   залежностей і поклав збірку ВСІМ чатам одразу.)
4. **Тихий успіх заборонено.** Команда, що не зробила роботу, мусить впасти
   гучно, а не відзвітувати «ок». (У нас: деплой «пройшов» з кодом 0, нічого
   не задеплоївши; червоний CI змерджено, бо `| tail` з'їв код виходу.)
5. **Канал зв'язку = git-файли, не чат-повідомлення.** Інбокс-файл доїде
   завжди; нудж між сесіями — це дзвінок «глянь інбокс», а не сам лист.
6. **Зелені тести ≠ робоча фіча.** Після деплою — жива перевірка на проді
   незалежним запитом.
7. **Доводити до кінця.** «Зробив 4/6 і питання» власник читає як «готово».
   Або фініш, або явний рядок у беклозі з причиною.

## 5. Як виглядає робочий день системи

1. **Ранок.** Власник відкриває координатора, той: git status → інбокс →
   WORKSTREAMS → звіт «за ніч: X змерджено, Y чекає рішення».
2. **Роздача.** Власник відкриває 2-5 робочих чатів стартовим промптом
   (готовий шаблон — у стартер-кіті). Кожен: worktree → задача.
3. **День.** Чати працюють автономно; здають PR; low-risk мерджать самі;
   ризикове падає координатору в інбокс. Власник відповідає лише на
   бізнес-«так/ні».
4. **Здача.** Кожен чат: PR-лінк + 3-7 рядків у лог дня + оновлений рядок
   WORKSTREAMS. Координатор деплоїть, верифікує живим запитом.
5. **Ніч.** Автоматика: експорт сесій (L1), вижимки (L2), реіндекс пошуку.
   Жодних нічних повідомлень людям.

## 6. Чого в цій ролі НЕМАЄ

- Немає «агент сам вирішив і задеплоїв у продакшн платіжну зміну» — ризикові
  зони завжди проходять гейт координатора.
- Немає таймерів «перевіряй щоN хвилин» — тільки подієва модель (прокинувся →
  прочитав інбокс). Таймер-петлі з'їдають ліміти токенів впусту.
- Немає видалення файлів з дисків власника. Ніколи. Це не техніка — це довіра.
- Немає усних домовленостей: не записано у файл → не існує.
