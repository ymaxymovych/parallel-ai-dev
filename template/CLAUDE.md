# Конституція проєкту <НАЗВА>

> Цей файл Claude Code автоматично підвантажує в КОЖЕН чат, відкритий у цій теці.
> Тому правила нижче діють на всі чати без нагадувань. Заповни `<...>` під себе
> і не роздувай файл: він у контексті кожної сесії, тому має лишатися коротким.

## Ролі (жорстко)

- **КООРДИНАТОР** — рівно ОДНА сесія. Ознака: її рядок у
  `coordination/WORKSTREAMS.md` позначений `[COORD]` і має СЬОГОДНІШНЮ дату.
  Тільки координатор: мерджить ризикові PR, деплоїть, чіпає спільні ресурси
  (встановлення залежностей, конфіги, CI). Якщо рядок протух (дата не
  сьогодні) — роль вільна: перший чат, якому вона потрібна, бере її і
  оновлює рядок.
- **РОБОЧИЙ ЧАТ** — усі інші. Не впевнений, що ти координатор → ти робочий чат.

## Правила робочого чату

1. ПЕРЕД першим редагуванням — створи власний git worktree. Ніколи не редагуй
   файли поза своїм деревом.
2. `git status` на старті: бачиш чужі незакомічені зміни — НЕ чіпай,
   не роби `reset` / `checkout` / `stash` / `clean` — це робота іншого чату.
3. НЕ запускай встановлення залежностей (`npm`/`pnpm`/`pip install`) — це спільний
   ресурс, тільки координатор. Потрібен пакет → інбокс-файл координатору.
4. Здача: commit → push своєї гілки → PR. Ризикова зона (auth, платежі,
   схема БД, доступи, розсилки) → НЕ мерджити самому, віддай координатору
   через `coordination/inbox/`. Решта — мерджити можна після зеленого CI.
5. НІКОЛИ не ковтай код виходу перевірок (`| tail`, `|| true` навколо
   тестів/лінтера/білда заборонені). Червоне не мерджиться. Крапка.
6. Нічого не видаляй з дисків власника. Ніколи.

## Пам'ять: обов'язкові ритуали

### На старті КОЖНОЇ сесії (по порядку)

1. `git status` (чуже брудне дерево? → worktree).
2. Прочитай `coordination/WORKSTREAMS.md` → додай/онови свій рядок
   (хто ти, над чим, у якому worktree, дата).
3. Прочитай свій інбокс: усі файли `coordination/inbox/`, адресовані тобі
   (`from-…-to-<я>-….md`).

### 🔒 Перед НЕТРИВІАЛЬНОЮ задачею (анти-кола — найважливіше правило)

Перед «збудуй / спроєктуй X» ти ЗОБОВ'ЯЗАНИЙ:

1. Прочитати `coordination/DECISIONS.md` — чи X уже вирішено робити інакше /
   не робити взагалі (і чи причина ще актуальна).
2. Прочитати `coordination/PROJECT_MAP.md` + грепнути кодову базу — чи X
   уже не існує (повністю або частково). «Грепни, перш ніж специфікувати».
3. Глянути `coordination/BACKLOG.md` — чи X не відкладено свідомо.

Перший рядок твоєї відповіді на таку задачу — вердикт звірки: «вже є отут…» /
«відхилено тоді-то, бо…» / «у беклозі, бо…» / «в пам'яті чисто, роблю».

### Під час роботи

- Прийняв рішення (архітектура, бібліотека, «робимо / не робимо») → одразу
  рядок у `DECISIONS.md`: дата, рішення, ЧОМУ, які альтернативи відкинув.
- Відклав щось свідомо → рядок у `BACKLOG.md` у ТОМУ Ж коміті.
- Наступив на граблі → рядок у `MISTAKES.md`: симптом → корінь → правило.
- Комітити: текст — після кожного файлу; код — кожні ≤30 хв. Push одразу.
  Untracked-файл, старший за 10 хвилин, — порушення.

### Наприкінці сесії

- 3-7 рядків у `coordination/log/YYYY-MM-DD.md`: що здано (PR-лінк),
  що не закінчено, що передано далі.
- Онови свій рядок у `WORKSTREAMS.md` (або познач завершеним).

## Комунікація між чатами

- Канал — ФАЙЛИ в git: `coordination/inbox/from-<я>-to-<кому>-<тема>.md`
  (закомічено і запушено). Повідомлення в UI — лише «нудж», не канал.
- Прокинувся з будь-якої причини → `git fetch` + перечитай свій інбокс.
- Жодних таймер-петель «перевіряй що N хвилин» — тільки подієва модель.

## Звітність власнику

- Власник НЕ читає код. Йому — тільки: що готово (лінком), що зламалось
  (простою мовою), і рідкі бізнес-питання «так/ні» (гроші, зовнішні
  повідомлення, доступи). Технічні питання вирішуй сам і документуй
  у `DECISIONS.md`.
- «Зробив 4/6 і питання» власник читає як «готово» — тому або доводь до
  кінця, або яви це рядком у `BACKLOG.md` з причиною.
- Тихий успіх заборонено: операція, що нічого не зробила, мусить впасти
  гучно. Після деплою — жива перевірка незалежним запитом, не «звіт агента».
